One file per decision, numbered and never renumbered. Amended, never rewritten: a
superseded ADR keeps its number and gains a pointer, because the reasoning behind a
decision that was later reversed is usually the most useful thing here.

**The `Status` row says whether the decision is in the tree.** A bare `Accepted` means built.
Anything else qualifies it — `not built`, `partly built`, `declared, not enforced`,
`superseded in practice by ADR-nnn` — with one line of why. Without that, a decision that was
deferred and a decision that shipped look identical, and the set stops being usable as a
description of the system (DOCX-042, DOCX-046).

| [046](046-a-replacement-meets-the-running-version-at-a-position.md) | A blue/green replacement cuts over when the two versions have consumed **exactly the same input**, compared as source positions per partition with both feeds stopped -- not at a wall-clock instant, which for two queries running at different speeds is either dropped records or doubled ones. | [047](047-the-image-is-a-dockerfile-over-built-artefacts.md) | The engine node's container image is a Dockerfile over artefacts the reactor has already produced -- not Jib, which cannot resolve its base image inside the offline gate and writes no `HEALTHCHECK`, and not distroless, which has no shell and would mean a second copy of the Arrow `--add-opens` somewhere nobody maintains. | [048](048-a-debug-fork-is-a-second-computation-nothing-can-read.md) | A time-travel debug session is a second computation of the same plan, on lanes of its own, restored from a retained checkpoint and stepped by hand. Isolation is three absences rather than a mode -- no sink is attached, the fork's view is in no catalogue, and the lanes are never shared -- because a `DEBUG` flag consulted before each write is a convention with a stronger name. Determinism is arranged from four things and costs one: the replay interleaves partitions in a fixed order, so a bug that depends on one particular interleaving may not reproduce. A breakpoint is one column against one value and deliberately not a language. An exported fixture replays the input from empty rather than carrying the checkpoint, and its expectation is *rehearsed* through a second empty execution so that the number in the file is one this engine has produced -- **built** |
| [049](049-an-ordered-index-over-the-keys-last-column.md) | `RANGE (column)` declares an ordered index over the key's **last** column, and this engine builds no other index over a view: a secondary index over a non-key column has to find the entry to delete from the row's previous values, and getting that subtly wrong leaves an index disagreeing with the view it indexes. Reads design §17.2's `INDEXED BY (user_id) RANGE (window_end)` as what it says — `INDEXED BY` is the key, `RANGE` adds an order to its last column. Records that the declaration is a *check* (`PRV-2073`, at registration, against the planned columns) rather than an allocation, so nothing new travels in the registry journal; that the index is one entry per visible key and therefore bounded by the ceiling that already bounds the view, and does not spill; and that an access path may change what a read costs and never what it answers, which is tested against a scan rather than argued — **built** |
| [050](050-a-tenant-owns-names-and-state-and-shares-only-with-itself.md) | A tenant owns the names it registers, the computations behind them and the keys their views hold. It does not own view names, reads, sources, sinks or lanes. Two admission quotas, `max-queries` and `max-state-keys`, are refused by name at registration (`PRV-8020`, `PRV-8021`) and never enforced on a running query. State is counted in view keys, the one measure each computation owns alone. The tenant is in the fingerprint, so identical SQL is shared within a tenant and never across tenants, for three reasons: accounting, blast radius, and disclosure by timing. A replacement from another tenant is `PRV-8022`. Operators read `GET /api/v1/tenants` and the `pravaha.tenant.*` meters. Single-node, since ADR-045 is on hold — **built**, with the console's tenants screen |

| [054](054-an-ordered-source-is-shared-at-an-exact-seam.md) | An ordered, exactly-once source is shared by meeting at an exact seam. | [055](055-an-equality-index-over-a-column-outside-the-key.md) | `INDEX (column)` keeps an equality index over one column outside a view's key, used by `=` and `IN`. The entry to delete is filed under the row the view held -- read under the view's monitor in the commit that replaces it -- never under the retraction, so the index is a function of the view by construction. Refuses `FLOAT`, `DECIMAL`, `BYTES` and the whole key (`PRV-2074`); at most four per view, on the heap, bounded by the view's ceiling; journalled as an `X` record in the same write as the registration, and carried across a replacement by column name. The view's counters, not `EXPLAIN`, show a read probed |
| [056](056-queries-on-queries.md) | A continuous query whose `FROM` names another query follows that query's **answer** -- its snapshot, then each commit's rows leaving (−1) and entering (+1), computed in the view's own commit -- not its changelog, which for a keyed upsert view is not how the answer changed. Fed through an ordinary pump; filter, projection and unwindowed `COUNT`/`SUM`/`AVG` (keyed too, bounded by the upstream's ceiling) run, windows, joins, `MIN`/`MAX` and `COUNT(DISTINCT)` are `PRV-2075`. Exactly once by carrying the **consumed answer** in the checkpoint and feeding the difference against the upstream's snapshot on restore, not an upstream commit number. Drop with dependants `PRV-8024` (no cascade), cycles `PRV-8025`, replacement of a chain member `PRV-8026`, depth 8 `PRV-8027`; reads authorised against the base streams (SX-11), same tenant only -- **built**, single node |
| [057](057-alerts.md) | An alert follows one view's answer (ADR-056) and says when a key's row **enters** it (fired) and when it **leaves** (cleared) -- retractions make clearing honest. Conditions are `column op literal AND ...` over the view, anything richer is a query over it. What is true (`fire_after`, `clear_after`) and what is said (`dedupe` deferred and converged, pause, snooze, reminders until `ACK`) are kept apart. Exactly-once state -- every decision journalled and forced before a send, no re-fire and no lost clear across a restart -- and at-least-once delivery under a stable idempotency key. Notifier channels are plugins bound as `pravaha.notifiers.*` (`webhook`, HMAC-signed with secrets by reference only, and `log`; email, Teams and PagerDuty designed). An `ALERT` catalogue object; `NOTIFY` needs `WRITE` on a `NOTIFIER`; a view with alerts cannot be dropped (`PRV-8024`) -- **built**, single node |
