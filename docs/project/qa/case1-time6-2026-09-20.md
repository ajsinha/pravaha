## 1. The test could not see it, and now can

`CaseStudySqlTest` planned every study's SQL against `schemaOf`, a fixture that never called
`StreamSchema.Builder.eventTime`. It therefore had exactly the gap the studies had, was green over
four windowed queries that could never have emitted a row, and would have stayed green after a fix
that only touched the studies.

**Fix.** The fixture reads `stream.<name>.event-time` from each study's own
`schema/streams.properties` — the key spelled as the server spells it — and marks the column. A
stream carrying a `TIMESTAMP` column and declaring no event time fails by name.

**Proof, taken before anything else was touched.** `CaseStudySqlTest` 6 run, **3 in error**, each:

```text
java.lang.IllegalStateException: banking-card-velocity's stream 'card_auth' carries a TIMESTAMP
column and declares no event time. Add stream.card_auth.event-time to its
schema/streams.properties (and pravaha.streams.card_auth.event-time to the application.yaml it
ships): without it no watermark advances over the stream and no window over it can ever close.
```

A seventh case was added — `everyStudyConfiguresTheEventTimeItIsPlannedWith` — because two files
now say which column is the event time, the fixture's and the `conf/application.yaml` a reader
actually starts a node with, and a study where they disagree is CASE-1 again with one more place to
hide it.

## 2. What each study needed

Every one declares its event time. Four of them window; `trade-processing` does not, and still
declares it, because retention is in event time and nothing else and `FOR SYSTEM_TIME AS OF` asks
each dimension table as of that column.

| Study | Stream | Event time | Also needed |
|---|---|---|---|
| `banking-card-velocity` | `card_auth` | `auth_time` | `deletes: detect` |
| `biology-sequencing-qc` | `read_metric` | `called_at` | `deletes: detect` |
| `trading-order-flow` | `order_event` | `event_time` | `deletes: detect` |
| `finance-counterparty-exposure` | `settlement` | `value_time` | a `value_ns` cursor, and `watermark.moves.on.update: false` |
| `trade-processing` | `trade` | `trade_time` | — |

**The directory shipped no `application.yaml` at all**, and no study said how to start a node, so a
reader following one literally had nowhere to put the declaration. Each study now ships
`conf/application.yaml` — `pravaha.streams`, `pravaha.sources`, `pravaha.lookups` — and has a "start
the node" step that quotes the settings that decide whether it works. `SETUP.md` gains the section
that is identical everywhere, including the one thing the studies never said: the connector is not
in the server jar, so `filesystem` aside, every one of them needs its plugin built into it or the
first registration fails with `PRV-5090`.

**Two things the declaration alone would not have fixed**, both found by writing the configuration
out and reading what the engine does with it:

* **`deletes: detect`, on the three Aerospike studies that aggregate.** A `lut-scan` re-reads an
  updated record as a new row and retracts nothing, so it *repeats rows* — and the registry refuses
  an aggregate over a source that repeats with `PRV-2042` (SCAN-1). Three of the five studies are
  `COUNT`/`SUM` over an Aerospike scan, so the binding a reader would have written from the
  connector page is refused before the event time ever matters. `trade-processing` is a projection
  and lookup joins, which SCAN-1 admits, and keeps the default.
* **The finance study's cursor.** The `jdbc` source stamps every row's event time with its
  **watermark column** (`JdbcPartitionReader:213`), not with the stream's declared event-time
  column. Polling on `payment_id`, which is what the study documented, would have stamped every
  payment with an instant in 1970, and no hour of 2026 could close however the stream was declared.
  So `data/schema.sql` gains `value_ns` — `value_time` in epoch nanoseconds, a stored generated
  column, indexed with `payment_id` — the binding polls on it, and the README says why there are
  two columns for one instant. What a value-time cursor cannot see (a payment booked with a value
  time older than one already read) is stated, with `postgres-cdc` named as the answer for a ledger
  where that happens.

## 3. The prose that defended the failure

`banking-card-velocity`'s README said **"Nothing appears yet, and that is correct"**, offered a
remedy that could not work (insert a row past the end of the minute — nothing was reading
`auth_time` as time), and closed with "The engine is not slow; it is refusing to publish an answer
it might have to retract." It now says which row closes the window and why — past the end **plus
the stream's out-of-orderness** — gives the insert and the `pravaha query` that shows the answer,
and then says what taking `event-time` out would actually do: not slow, never.

`SETUP.md`'s *A note on time* said study-wide that "If you load ten rows and see no output, that is
usually correct and not a bug". It now says event time is declared rather than inferred, shows the
key, states that a windowed query over a stream without it is refused, and then explains waiting
correctly. Every README was read for the same shape:

| Study | What it said | What it says |
|---|---|---|
| `banking-card-velocity` | "Nothing appears yet, and that is correct", with an unworkable remedy | the row that closes the minute, and what the declaration does |
| `biology-sequencing-qc` | "Windows close on data, not on the clock… by hand, bump the timestamp" | the exact `called_at` that publishes the window, and the declaration behind it |
| `finance-counterparty-exposure` | "The 09:00 hour closes when a payment with a `value_time` at or after 10:00 arrives" | at or after **10:01**, the out-of-orderness included; and that this is waiting, not stalling |
| `trading-order-flow` | nothing — the study never said its windows were open | a note giving the event that publishes the first hopping windows |
| `trade-processing` | "No window here, so nothing is waiting on a watermark" — true | unchanged, plus why it declares an event time anyway |

## 4. The refusal

`PhysicalPlanBuilder.requireDeclaredEventTime` refuses a windowed plan over an unbounded input
whose stream declares no event-time column, with `PRV-2002`:

```text
PRV-2002  TUMBLE is given DESCRIPTOR(event_time), but 'txn' declares no event-time column -- so no
          watermark advances over it and no window this query opens can ever close. It would
          register, report RUNNING, ingest every row and emit nothing, for ever.
            Declare the column: pravaha.streams.txn.event-time: event_time, or 'eventTime' on
            POST /api/v1/streams. The column must be a TIMESTAMP.
          Refused at registration rather than discovered from an empty view later.
```

Lifted from `a0a2d9a` as the lead's note said it could be, with **one correction that the case
studies found**: the original asked `input.outputSchema().eventTimeOrdinal()`, and a **join's**
output schema is built from two sides and carries neither side's marker. So the original refused
every windowed query over a lookup join — four of the five case studies, all of them correct, and
that is why they appeared in the 54. The check now asks the **source** schema (`sourceSchemaOf`,
the leftmost leaf, the same descent that already gave the message its stream name), because the
watermark is the source's. Without that correction the studies would have been "fixed" and still
refused.

Only for an unbounded input: over a bounded read the windows are fired by `finish()` at the end of
the scan, so the same SQL still plans and still answers.

### The two recorded outcomes, rewritten

* **`WindowAnswerTest.win005`** — was
  `..._tumbleOverAStreamWithNoDeclaredEventTimeNeverFiresRatherThanRefusing`, now
  `..._tumbleOverAStreamWithNoDeclaredEventTimeIsRefusedAtRegistration`. It asserts the refusal by
  code, that it names the stream and the key, and that nothing was half-registered under the name.
  Its control — the same shape over a stream that *does* declare one — is unchanged and still
  passes in the same run, so the refusal is about the declaration and not about a dead server.
* **`EventTimeTest.time002And009`** — was `..._aStreamWithNoDeclaredEventTimeIngestsEverything-
  AndServesNothing`, now `..._aStreamWithNoDeclaredEventTimeIsRefusedRatherThanRunForEver`, with a
  second case beside it: the same query over the same stream **runs** once the event time is
  declared, and gives TIME-001's eleven windows. The old outcome described the engine accurately
  and was still the wrong thing to keep.

Both carry the reason and the owner's rule in the body: *"Where the engine could accept something
doubtful or refuse it, it refuses — by name, with a code and the way to say it properly. Silent
coercions, guessed units and papering defaults are the bugs nobody finds."*

### What the refusal broke, and how

**52 tests in `pravaha-it` failed in one run with nothing else changed** — `Tests run: 829,
Failures: 3, Errors: 49` — of which **49 are the refusal**; the other three are `ErrcClientTest`
looking for a `-cli.jar` the `test` phase does not build, which is unrelated and fails the same way
without this change. Every one of the 49 but the three below is a fixture carrying a timestamp
column without declaring it, and declaring it is the fix:

| Fixture | Reached |
|---|---|
| `LifecycleTestSupport.TXN` | `LifeRegistrationTest`, `LifeDropTest`, `LifeFailureTest`, `LifePauseTest`, `LifeRestartTest`, `LifeResumeTest`, `LifeSharingTest`, `LifeSqlTest` |
| `ContinuousQueryAnswerTest.TXN` | 19 CQ cases |
| `SqlAnswerTest.txn()` | the windowed SQLX cases and two `COUNT(DISTINCT)` cases |
| `ServedQueryTest.txn()`, `LookupJoinTest.orders()` and its `txn` | 5 cases |
| `CaseStudySqlTest`'s fixture | 3 cases — and these were the join bug above, not a missing declaration |

After the fixtures, the join correction and the CLI option: `pravaha-it` **829 tests, 0 failures, 0
errors, 4 skipped**. The gate over the 29 modules through it —
`./mvnw -o -pl pravaha-it,pravaha-cli,pravaha-sql -am verify` — **3,494 tests, 0 failures, 0
errors, 67 skipped**, with **1 `BUILD SUCCESS` and 0 `BUILD FAILURE`** counted separately. `DocumentationFreshnessTest`,
`FindingsRegisterTest`, `HelpExamplesSqlTest` and `SourceFileSizeTest` 31 run, 0 failures. The
console's `test_help.py` 33 passed.

**And one product gap, which is the interesting one.** `pravaha validate --schema
"id:INT64,…,event_time:TIMESTAMP"` has no syntax for marking the event-time column, so after the
refusal the CLI could not validate any windowed query — `ErrcSqlTest`'s own vacuity check caught
it. `validate`, `explain` and `run` now take `--event-time <column>`, spelled as the node's
configuration spells it, through one shared `SchemaOption.parse` so the three cannot drift into
telling an operator a query is fine that a node refuses. `ErrcSqlTest` asserts both halves: the
rewrite validates with the option, and is refused without it.
